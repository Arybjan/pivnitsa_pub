# Venue Service

Сервис разработчика №3: залы, столики, вместимость, схема зала, физическая доступность и блокировки администратора. Python 3.12, FastAPI, SQLAlchemy, PostgreSQL, Alembic. Сервис запускается отдельно от Auth и Booking и использует собственную базу данных.

## Запуск

Из корня репозитория:

```bash
cd services/venue-service
cp .env.example .env
```

В Windows вместо `cp` можно использовать `Copy-Item`. Укажите в `.env` `JWT_SECRET_KEY` из Auth Service длиной не менее 32 символов. Затем:

```bash
docker compose up --build
```

API: http://localhost:8003. Swagger: http://localhost:8003/docs. База PostgreSQL доступна локально на порту 5433. Миграции применяются при запуске контейнера. Пароль `venue` в примере предназначен для локальной разработки; для сервера задайте собственный пароль.

Без Docker:

```bash
python -m venv .venv
python -m pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --reload --port 8003
```

Перед установкой активируйте окружение: `.venv\Scripts\Activate.ps1` в PowerShell или `source .venv/bin/activate` в Linux. Для локальной проверки без PostgreSQL можно задать `DATABASE_URL=sqlite:///./venue.db`. В рабочем окружении используется PostgreSQL.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET / POST | `/api/v1/halls` | Список / создание зала |
| GET / PATCH / DELETE | `/api/v1/halls/{id}` | Чтение / изменение / удаление зала |
| GET | `/api/v1/halls/{id}/map` | Схема со столиками и физической доступностью |
| GET / POST | `/api/v1/tables` | Список / создание столика |
| GET / PATCH / DELETE | `/api/v1/tables/{id}` | Чтение / изменение / удаление столика |
| POST | `/api/v1/tables/availability` | Пакетная проверка физической доступности |
| GET / POST | `/api/v1/tables/{id}/blocks` | Список / создание блокировки |
| DELETE | `/api/v1/tables/{id}/blocks/{block_id}` | Снятие конкретной блокировки |
| GET | `/health` | Состояние процесса |
| GET | `/health/ready` | Готовность базы после миграций |

Списки поддерживают `offset` и `limit` (до 200). У списка столиков есть фильтры `hall_id` и `min_capacity`. Карта возвращает все столики зала.

Создание столика:

```json
{
  "hall_id": 1,
  "number": 15,
  "capacity": 4,
  "x": 0.35,
  "y": 0.6,
  "rotation": 0,
  "status": "ACTIVE"
}
```

Координаты `x` и `y` находятся в диапазоне 0–1 относительно схемы зала; начало координат — левый верхний угол. `map_width` и `map_height` задают размер схемы, `map_image_url` — необязательный HTTP(S) URL фонового изображения. `rotation` задаётся в градусах от 0 включительно до 360 исключительно.

Номер столика уникален внутри зала. Удаление мягкое: строки и идентификаторы сохраняются для истории бронирований, но удалённые объекты исчезают из API. Старый номер можно использовать для нового столика с новым ID. Зал со столиками удалить нельзя; его можно отключить через `is_active=false`.

## Права доступа

Чтение залов, столиков, схемы и проверка физической доступности публичные. Изменения и просмотр причин блокировок требуют `Authorization: Bearer <access_token>`.

Сервис проверяет JWT HS256 с общим секретом Auth Service. Поддерживаются переменные `JWT_SECRET_KEY` и `JWT_SECRET`. Обязательны `sub`, `exp`, а также `token_type=access` или `type=access`. Для изменения нужна роль `admin` / `owner` либо список `permissions`, содержащий `venue:write`. `is_active=false` запрещает доступ. Refresh token не принимается. Выпуск токенов остаётся в Auth Service; этот контракт нужно использовать при интеграции с ним.

## Доступность и интеграция с Booking

`Table.status` содержит только `ACTIVE` или `UNAVAILABLE`. Статусы бронирования, резервирование, даты мероприятий, цена и платежи в этом сервисе не хранятся.

Административная блокировка содержит `starts_at`, `ends_at`, необязательную причину `reason`. Даты должны содержать часовой пояс. Интервал полуоткрытый: `[starts_at, ends_at)`. Любое пересечение интервала блокировки с запрошенным интервалом делает столик физически недоступным. Несколько блокировок могут перекрываться; снятие одной не отменяет остальные.

Booking может выполнить:

```http
POST /api/v1/tables/availability
Content-Type: application/json
```

```json
{
  "table_ids": [15],
  "starts_at": "2030-08-20T18:00:00Z",
  "ends_at": "2030-08-21T02:00:00Z",
  "guests": 4
}
```

```json
[
  {"table_id": 15, "physically_available": true, "reason": null}
]
```

До 200 ID в запросе; повторяющиеся ID возвращаются один раз. Причины недоступности: `NOT_FOUND`, `HALL_INACTIVE`, `TABLE_UNAVAILABLE`, `ADMIN_BLOCK`, `INSUFFICIENT_CAPACITY`.

Для карты можно передать оба параметра `starts_at` и `ends_at`. Без них проверяется физическое состояние на `checked_at`. Параметр даты из календаря клиент или Booking преобразует в нужный интервал с часовым поясом.

`physically_available=true` не означает отсутствия брони. Booking отдельно проверяет занятость и защищает создание брони транзакцией и ограничениями своей БД. Для итоговой карты клиент или агрегатор совмещает данные Venue с занятостью из Booking: физически недоступные столики показываются недоступными, остальные — свободными или занятыми по данным Booking. Сервис Venue не вызывает отсутствующие в текущем Booking API методы и не меняет его БД.

Проверка доступности — снимок, она не резервирует столик. Блокировка не отменяет уже существующие брони; синхронизацию таких изменений и правила обработки существующих броней нужно согласовать с Booking. Ограничение глубины бронирования и запрет прошедших дат относятся к Booking.

## Проверки

```bash
python -m pip install -r requirements-dev.txt
ruff check .
black --check .
pytest -q
```

Без `TEST_DATABASE_URL` тесты используют временные SQLite-базы. Для PostgreSQL задайте `TEST_DATABASE_URL=postgresql+psycopg://user:password@localhost:5432/venue_test`. Тесты создают и удаляют собственные случайные схемы, поэтому пользователю БД требуется право `CREATE`. Проверяются API, права, интервалы блокировок, ограничения БД и миграции в обе стороны. GitHub Actions запускает тесты с PostgreSQL 17 при изменении сервиса.

Сервис покрывает серверную часть US-13, US-16, US-17, US-31 и физическую составляющую US-15. Мобильная карта и веб-интерфейс администратора используют этот API и разрабатываются отдельно.
